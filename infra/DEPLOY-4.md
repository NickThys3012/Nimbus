# Deploying issue #4 (CI pipeline: build and test both the API and the Angular app on every PR) to the VPS

## Nothing to deploy — this is CI-only

Issue #4 adds `.github/workflows/ci.yml`, which runs in GitHub Actions on every PR and on
push to `main`. It does not touch anything that runs on the VPS:

- No changes to `infra/docker-compose.prod.yml` / `/opt/nimbus/compose.yaml`.
- No changes to `Dockerfile`, `infra/Caddyfile`, or any container image tag.
- No new environment variables/secrets to add to `/opt/nimbus/.env`.
- No new services, ports, or volumes.

**There is no `[VPS]` step for this issue.** Skip straight to whatever the next `infra/DEPLOY-*.md`
is when one lands.

## What issue #4 actually changed `[LOCAL / GitHub]`

Three jobs, all defined in `.github/workflows/ci.yml`:

1. **`dotnet`** — `dotnet restore` → `dotnet build` (Release, `SkipSpaBuild=true` so this job
   doesn't need a Node toolchain) → `dotnet test` across all four test projects
   (`Nimbus.Domain.Tests`, `Nimbus.Application.Tests`, `Nimbus.Infrastructure.Tests`,
   `Nimbus.Api.Tests`), collecting `.trx` results and Cobertura coverage per project.
   `TreatWarningsAsErrors` was already `true` in every `.csproj` (nothing new there); this job
   just makes sure `dotnet build` actually runs on every PR now.
2. **`angular`** — `npm ci` → `npm run lint` → `ng test --no-watch` (Vitest, headless by
   default — no browser/Chrome install needed) with Cobertura + JUnit output → `ng build
   --configuration production`. The production `dist/Nimbus.Web/browser/` bundle is uploaded as
   the `angular-dist` build artifact.
3. **`publish`** (needs both of the above) — downloads `angular-dist`, runs `dotnet publish
   Nimbus.API/Nimbus.API.csproj -p:SkipSpaBuild=true`, then copies the Angular bundle into the
   publish output's `wwwroot/`. Uploads the result as the `nimbus-app` artifact — one artifact
   that deploys the whole app, matching how `Dockerfile`'s `api` target already stitches
   `web-build`'s output into `/app/publish/wwwroot`.

Both `dotnet` and `angular` post their test results as GitHub PR checks (via
`dorny/test-reporter`) and a coverage summary table into the job's step summary (via
`danielpalme/ReportGenerator-GitHub-Action`) — both show up on the PR without needing to open the
raw logs. ReportGenerator was picked over `irongut/CodeCoverageSummary` (the initial choice)
because coverlet emits an empty `<packages/>` cobertura file for test projects with no
instrumentable app code of their own (e.g. `Nimbus.Domain.Tests`/`Nimbus.Application.Tests`), and
irongut's action hard-fails the job on those ("No package data found"); ReportGenerator merges
all per-project cobertura files and silently skips the empty ones.

### Angular tooling added

No lint or coverage tooling existed on the Angular side before this issue, so the following were
added to `Nimbus.Web`:

- `@angular-eslint` + `eslint.config.js` (from `ng add @angular-eslint/schematics`), with the
  generated `src/app/core/api-client/**` excluded from linting (it's generated by
  `npm run generate:api`, not hand-written) and the two selector-style rules
  (`@angular-eslint/component-selector` / `directive-selector`) turned off — the app's existing
  components intentionally use a capitalized `Nimbus` prefix (`Nimbus-root`,
  `Nimbus-user-by-mail`, ...), which neither rule's `camelCase`/`kebab-case` style option can
  express without a wider rename.
- `@vitest/coverage-v8`, so `ng test --coverage` works.
- Two pre-existing test bugs that would otherwise fail `ng test` on `main` right now: a bad
  named import in `user-by-mail.spec.ts` (the component is a default export) missing the
  `BaseHttpRequest`/`OpenAPI` DI providers its `AuthStore` dependency needs, and a stale
  `Nimbus.spec.ts` assertion checking for an `<h1>` that no longer exists in the template.

### Caching

`actions/setup-dotnet` caches NuGet packages (keyed on `**/*.csproj`, since there's no
`packages.lock.json` yet) and `actions/setup-node` caches `~/.npm` (keyed on
`Nimbus.Web/package-lock.json`) — both via each action's built-in `cache` input, no separate
`actions/cache` step needed.

## What issue #4 does *not* do

- **No CD.** Nothing here pushes images to `ghcr.io` or touches the VPS — building/pushing
  `nimbus-api`/`nimbus-migrator` stays the manual process from `infra/DEPLOY-2.md` step 2 until
  issue #6's CD pipeline lands.
- **No fork-PR check-run workaround.** `dorny/test-reporter` needs `checks: write`, which
  GitHub only grants to workflows triggered from the same repo (not PRs from forks). Since this
  repo doesn't currently accept external-fork PRs, the simpler single-workflow setup was used
  instead of the two-workflow (`pull_request_target`) split `dorny/test-reporter`'s docs
  recommend for public repos accepting fork PRs. Revisit if that ever changes.
